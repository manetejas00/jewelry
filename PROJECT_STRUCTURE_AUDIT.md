# Project structure audit

The storefront and Studio are a React/Vite SPA served by Express. The Express entry point registers middleware, starts the database and server, and contains many domain routes. Knex uses SQLite in preview and MySQL in production. The audit examined application entry points, the static import graph, the 26 ordered migrations, seeders, release scripts, and the automated suite.

| Area | Findings |
| --- | --- |
| Storefront, Studio, shared UI | The 2,938-line `src/main.jsx` combines layout, routing, catalogue pages, checkout, and Studio administration. Studio tabs already have separate components for several domains. Common lists, filters, badges, pagination and dialogs exist. Offers can move as a unit with its editor. |
| State and HTTP | `store.jsx` owns catalogue refresh, cart, saved items and customer synchronization. `api.js` handles request timeouts, both CSRF headers, session expiry and overlapping catalogue reads. Keep the cart and wishlist together where their revision and guest merge semantics are shared. |
| Server and permissions | The 890-line entry point mixes account and OTP workflows, review moderation, media, supplier operations and pricing. Staff role rechecks and customer CSRF are distinct policies. Moving middleware or overlapping routes can silently change which handler wins. |
| Catalogue | Jewelry, Coin and Kurta already have route, controller, service, repository, mapper and policy layers. Legacy storefront, imports, search, reviews and checkout still depend on `products` or legacy-compatible `coins`. The Coin router aliases overlap later admin routes. A wholesale cutover requires reconciliation of reads, writes, SKU lookup, stock and existing orders. |
| Database and inventory | Migrations already add lookup indexes, checkout integrity, independent catalogue tables and import tracking. Quote and checkout use server-side pricing, and checkout and publish use transactions. Some catalogue/export paths materialize whole collections, and some services still query Knex directly. Profile representative MySQL data before changing queries or adding indexes. |
| Pricing, offers, shipping, payment | Pricing uses Decimal, approved rate freshness, product rules, offers, and merchant shipping configuration. COD is the supported checkout mode. The existing payment event schema and configuration guard do not constitute an online provider implementation. |
| Integrations | OTP, SMTP, external supplier feeds, chatbot and AI copy have different configuration and failure semantics. The chatbot already has routes, service, persistence and provider boundaries. Recommendations use local catalogue logic. Production environment validation is already centralized in `runtime.js`, while supplier settings are refreshed from the database. |
| Media and import/export | Sharp normalizes image uploads and builds derivatives. Upload handlers have different validation for review and merchant media. Supplier preview and transactional publish have compatibility aliases; exports and template downloads have established field names. |
| Duplication and dependencies | The size chart is duplicated byte for byte. Thumbnail URLs are composed through a backend-to-frontend import, while frontend media imports backend coin artwork. No cycles were found in the static relative JavaScript import graph. Two Studio route helpers have no callers. `catlog` is a tracked alias with compatibility value, so retain it. |
| Errors and configuration | The global handler already normalizes validation, malformed JSON and some Knex constraints. The native SQLite foreign-key error code is missing. Diagnostic URLs may include query credentials, such as reset tokens. Several environment values are validated at production boot but malformed origins and ports can still fail late in development. |
| Verification and scripts | CI runs the Node test suite and Vite build. There is no configured lint or formatter command. Several catalogue tests use the default SQLite file and mutate it, and legacy Kurta tests expect historical rows absent from the current catalogue seeder. Keep data cleanup and migration scripts out of verification against the workspace database. |

The first test run reported 218 passing and 28 failing. Local HTTP listeners were denied by execution restrictions, four Kurta checks failed from shared SQLite state or historical fixture assumptions, and HTTP fixture startup caused downstream failures. Isolate the catalogue tests and verify the HTTP suite with loopback access.

Prioritize moving route groups in place, isolating public shared data, and splitting Studio offers from the app entry. A later catalogue consolidation should start with a SKU and inventory reconciliation against a representative database copy, followed by endpoint parity and checkout tests. Keep reports, integration configuration, current routes and schema history available during that work.
